## Correctness and measurement gates

- `DashboardQueryService` calls asset type then account distributions sequentially on both a cache miss and a warm-cache asset refresh. The current `AssetsServiceInvestment` performs separate account loads and batched valuations for each. Its `IAssetsServiceTyped` registration is scoped, so E03's dictionary can share work in that composition. These facts support the hypothesis; they do not establish every same-scope caller is read-only. The patch's tests cover order, key isolation, failed valuation retry and value semantics, but **no write followed by a same-key read in one scope**. Audit call paths and add invalidation or constrain the snapshot to the read composition before shipping. Also confirm whether any same-instance concurrent caller is possible; the proposed dictionary is unsynchronized.
- BenchmarkDotNet measured **in-process API work over local SQLite**, not HTTP transport, browser paint, production database behavior or user-perceived page load. Most A/B cases have one candidate run; within-run 99.9% error intervals are not a between-run significance test. Several runs have material baseline drift. E03's earlier shared-directory candidate artifacts were excluded after a collision; use its replacement run only. E05's baseline process exit was not directly captured, though completed artifacts and logs exist. These limitations preclude a broad speedup claim.
- E01's domain benchmark avoids API setup and shows a real algorithmic mechanism only. E02's extra-query explanation is an inference without SQL/query-count instrumentation. E04's one-month candidate result excluded one BenchmarkDotNet outlier. E06 has no counterfactual. Do not combine their percentages into a dashboard gain.

## Next iteration: one experiment now

1. **E03 warm-cache confirmation only.** Apply the exact preserved E03 patch in an isolated, verified worktree state. With an unchanged seed/hash, same SDK/config and no concurrent benchmark, run four **sequential** warm `DashboardBenchmarks` sessions in A/B/A/B order (baseline/candidate/baseline/candidate), each with separate artifact directory and captured command exit. Validate that each run completed both overview windows and collect full JSON mean, median, variability and allocated/op. Keep the six-month endpoint as the primary outcome, one-month as a guardrail. Compare the two candidate runs with their adjacent baselines, not solely overlapping within-run CIs. If the six-month gain and allocation reduction do not replicate, stop E03. If they do, audit scope/write paths and add a same-scope mutation test or restrict the snapshot to the dashboard read operation before recommending adoption. Restore the candidate after measurement and verify the original unrelated worktree changes remain.

No E01 long-held-bond API fixture **now**: the current endpoint data shows no timing benefit, and manufacturing a favorable fixture alone would not establish a user workload. Revisit when profiling, data distribution or an explicit long-held-bond performance target shows that such pricing materially contributes to overview latency. No E02/E04/E05/E06 follow-up benchmark is worth the current cost. This is a stopping rule for the present round after E03 confirmation, not a claim that all future optimization is exhausted.

## Proposed issues (do not publish yet)

1. **Conditional E03 implementation issue, only if confirmation and freshness gate pass.** Scope: share one investment account/valuation snapshot for the two dashboard end-asset distributions in a request; preserve exact user, currency and timestamp isolation, negative type totals, positive account rows and failed-call retry. Acceptance: one account enumeration and one valuation in the overview/refresh read composition; same-scope writes cannot return stale data; no cross-request sharing or unsafe concurrent access. Validation: focused unit tests including write/read freshness, integration test for warm overview distribution parity, passing repository unit suite, and repeated interleaved warm API measurements with raw artifacts and captured exits. Do not assert a browser improvement without browser evidence.
2. **Deferred E01 workload issue, only when a real long-held-bond cost is established.** Scope: characterize the share of overview time spent rebuilding bond histories for realistic long-held portfolios, then evaluate the preserved request-local history patch if material. Acceptance: exact per-date parity through gaps, posting and rate boundaries; unchanged freshness; a repeatable API-level gain on the representative workload. Validation: profile/query timing or representative data first, paired cold/warm API runs and unit parity tests. The existing domain result alone does not satisfy acceptance.

No issue proposed for E02, E04, E05 or E06 at this time.
